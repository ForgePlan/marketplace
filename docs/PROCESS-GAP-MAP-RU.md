# Карта дыр процесса SDLC/PDLC

Диагностический документ. Отвечает на вопрос «чего не хватает конвейеру, чтобы он был полным»
— по стадиям, по техникам, по требованиям.

Карта ничего не чинит. Она индекс: каждая дыра ниже заведена как GitHub issue, и работа идёт
по issues, а не по памяти. Номера — в разделе [Ранжированный список](#ранжированный-список).

Дата снятия среза: 2026-08-29. **Часть дыр с тех пор закрыта** — разделы ниже оставлены как
описание «до», а текущее состояние каждой строки смотрите в
[Ранжированном списке](#ранжированный-список). Закрыты: фазовый слой (§1.2), гейты NFR / DDD /
STRIDE (§2, §4), путь диспатча (§3.1), счётчики (§5), санитария (§6). Каждое число получено командой на диске, не из документации —
блок [Как перепроверить](#как-перепроверить) внизу воспроизводит их все.

## Как читать

У каждой техники и каждой стадии есть уровень зрелости. Уровень — не оценка качества, а ответ
на вопрос «что удержит дисциплину, когда о ней забудут».

| Уровень | Что значит | Пример |
|:---:|---|---|
| **T1** | Названа + определён выход + есть машинный гейт | C4, FPF ADI, BMAD Findings |
| **T2** | Названа + определён выход, гейта нет | DDD, GIVEN/WHEN/THEN сценарии |
| **T3** | Только карточка на 4 строки в роутинге | SRE, DORA, JTBD, 5 Whys — 20+ штук |
| **T4** | Не существует | story mapping, impact mapping, Wardley |

Разница между T1 и T2 не в том, насколько техника хороша. `/ddd-decompose` — 269 строк с
интервью, Mermaid и привязкой к артефактам, ничем не хуже C4. Разница в том, что у C4 есть
строка у `guardian`, а у DDD нет. **T1 держится сам. T2 держится, пока помнят.**

## 2. Требования: FR против NFR

Это самая асимметричная пара в системе.

| | FR | NFR |
|---|---|---|
| Секция в шаблоне | есть | есть |
| Структурная форма | `specification.md:203` | `specification.md:217` (category / threshold / measurement) |
| MUST-правило валидатора | `prd-fr-exist` | **нет ни одного** |
| Правила качества | `prd-fr-format`, `prd-measurability-adjectives`, `prd-vague-quantifiers`, `prd-orphan-frs`, `prd-no-impl-leakage` | **нет** |
| Строка у `guardian` | нет (делегирует валидатору) | **нет** |
| В MUST-списке `artifact-reviewer` | да (`:140`) | **нет** (`:140`) |
| Живое покрытие | **77 из 79 PRD** | **29 из 79 PRD** |

Правил с `nfr` в бинаре `forgeplan` нет — проверено извлечением всех идентификаторов `prd-*`.
Единственное упоминание NFR среди правил — сообщение `"Tech names in FR/NFR sections: "`, и
принадлежит оно правилу `prd-no-impl-leakage`: то есть единственное правило, которое вообще
читает секцию NFR, проверяет её на названия фреймворков, а не на измеримость.

Единственная «проверка» NFR во всей системе — буллет внутри промпта ревьюера
(`forge-cycle.md:557`, «Missing NFRs (performance, security, scalability thresholds)»). Его
машинное постусловие — наличие секции `## Findings`. Ревьюер, написавший одну находку про что
угодно, гейт удовлетворил.

Результат предсказуем: **50 PRD не имеют секции NFR вовсе, и ничто ни разу не возразило.**

### 2.1. Хорошая форма NFR уже существует — но нигде не закреплена

19 PRD используют такую таблицу:

```
| ID | Category | Requirement | Metric | Condition | Measurement |
| NFR-001 | Authority | Ответ недоступен агентам | 0 agent-authored ticks | все прогоны | аудит прав на Decision-задачах |
```

Это ровно то, чего требует прописанное правило «у каждого NFR должен быть метод измерения».
Поиск `Metric | Condition | Measurement` по всему маркетплейсу даёт **0 совпадений**: форма не
попала ни в один шаблон, ни в одного агента, ни в одно правило. Она живёт только в телах PRD
как привычка автора и умрёт вместе с ней.

### 2.2. Сценарии в SPEC — та же болезнь

Центральный инвариант `/spec-author`: «у каждого Requirement есть хотя бы один Scenario».
Заявлен в трёх местах прозой. Правил валидатора для SPEC ровно три — `spec-summary`,
`spec-contracts`, `spec-related`. Правила «Requirement без Scenario» нет.

Зубы появляются на стадию позже: `tdd-planner` HARD RULE 1 отказывается планировать против
SPEC без блоков `#### Scenario`, а хук `tdd-gate.sh` ловит дрейф после заморозки. То есть
инвариант держит не автор и не гейт, а следующий по конвейеру потребитель.

## 3. Продуктовая сторона (PDLC)

**В каталоге 23 плагина. Продуктовых — ноль.**

```
story map                  → 0 файлов
impact mapping             → 0 файлов
wardley mapping            → 0 файлов
opportunity solution tree  → 0 файлов
```

JTBD, Lean Startup и Double Diamond существуют — как три карточки по 4-6 строк
(`routing-map.md:244`, `:251`, `:258`) и как ячейка в строке 10 роутинга «Product discovery
(PDLC)». Ни агента, ни скилла, ни команды. Цепочка диспатча строки 10 переиспользует четыре
generic-агента (`brief-intake` → `research-analyst` → `goal-planner` → `specification`), в
телах которых слов «JTBD», «Lean» или «Double Diamond» нет вообще.

Сравнение с инженерными строками честно показывает разрыв: у строк BMAD / SPARC / TDD / CANVAS
есть свой плагин, мастер-оркестратор, фазовые агенты, точка входа и (у трёх из четырёх)
fail-closed хук. У строки 10 — три абзаца текста.

Отдельно: `forgeplan-brownfield-pack` даёт 12 скиллов извлечения требований (`scenario-writer`,
`use-case-miner`, `invariant-detector`, `intent-inferrer`, `ubiquitous-language`,
`causal-linker` и др.). Это **обратный** ход — вытащить домен из существующего кода. Прямого
хода, от пользователя к требованию, нет.

### 3.1. Известный дефект: сломанный путь диспатча

`routing-map.md:322` объявляет `research-analyst` профилем **A** с описанием «Produces NOTE
artifacts». Реально это **Profile C**: денилист запрещает `forgeplan_new`, `forgeplan_update`,
`forgeplan_link`. Он физически не может создать NOTE.

На него ссылаются два места: строка 10 (PDLC) и `project-agent-matrix.yaml:132` как
`shape.secondary`. **Оба пути диспатча сломаны** — агент вызовут, он отработает и не сможет
ничего сохранить.

Это не единичный случай: ещё 8 меток профилей в том же индексе присвоены агентам, у которых
денилиста нет вообще, то есть метка ничем не подкреплена.

## 4. Техники: C4 и есть ли аналоги

### T1 — техника + выход + гейт (всего три)

| Стадия | Техника | Выход | Гейт |
|---|---|---|---|
| Архитектура | **C4** | Mermaid L1+L2 в `docs/c4/<ADR-NNN>.md` | `guardian.md:186` → CONCERNS |
| Решение | **FPF ADI** | ≥3 секции `### Hypothesis` в EVID | `guardian.md:185` → **BLOCKER** |
| Ревью | **BMAD Findings** | секция `## Findings` с ≥1 пунктом | `guardian.md:183` → BLOCKER |

Плюс два полуслучая: delta-spec при supersede (`:187`, BLOCKER) и ground-truth verification
(`:188`, BLOCKER) — это дисциплины, а не стадийные техники.

C4 сделан образцово: 369 строк, интервью-скрипт, отдельный неинтерактивный dispatch-режим,
контракт идемпотентности, путь сохранения, отображение на артефакты forgeplan, и строка у
`guardian` с регэкспом детекции. Это эталон, по которому видно, чего не хватает остальным.

### T2 — техника + выход, но без гейта

| Техника | Реализация | Чего не хватает |
|---|---|---|
| **DDD bounded contexts** | `/ddd-decompose`, 269 строк, 9 шагов, Mermaid context map | строки у `guardian` |
| **GIVEN/WHEN/THEN** | `/spec-author`, шаблон Requirement → Scenario | правила валидатора (§2.2) |
| **STRIDE** | `security-expert` HARD RULE 5: каждая находка тегируется STRIDE/OWASP/CWE | нет `/threat-model`, нет DFD-выхода, нет гейта |
| **Event Storming** | 6-цветная нотация внутри `ddd-domain-expert` | нет артефакта, нет пути сохранения, нет привязки к forgeplan |

Проверка того же среза со стороны гейта: в `guardian.md` C4 упомянут 18 раз, ADI — 19,
delta-spec — 8, ground-truth — 3, BMAD — 1. **DDD, STRIDE, event storming, NFR, story mapping —
ноль упоминаний.**

### T3 — только карточка

SRE / error budgets, DORA, JTBD, Lean Startup, Double Diamond, 5 Whys, Fishbone, A3, Mikado,
Branch-by-Abstraction, Anti-Corruption Layer, Incident Command System, Blameless post-mortem.
Формат каждой — одно предложение, «когда работает», «когда не надо», источник. Для сравнения:
369 строк у C4 против 6 строк у SRE.

### T4 — не существует

story mapping, impact mapping, Wardley mapping, opportunity solution tree.

### Асимметрия одной строкой

Гейты есть у архитектуры, у выбора решения и у ревью. У декомпозиции, спецификации,
безопасности — выход есть, гейта нет. У продукта, эксплуатации, производительности, техдолга и
инцидентов — только имя техники в ячейке таблицы.

### 5.1. Про число агентов: дело не в дрейфе, а в определении

Первая редакция этой карты писала «97 файлов» и называла расхождение с «94» дрейфом. Это было
неверно, и вот точная картина:

| | |
|---|---|
| `agents/*.md` — верхний уровень | **94**, все настоящие агенты |
| `agents/*/*.md` — вложенный уровень | 3 файла: `discover/README.md`, `discover/SCAFFOLDING.md` (не агенты) и `discover/discover.md` (**агент, с денилистом**) |
| Настоящих агентов | **95** |
| С денилистом | **42** |

Дрейфа тут не было — было **слепое пятно счётчика**: `catalog-check` считал по маске
`plugins/<name>/agents/*.md` и внутрь папки агента не заходил, поэтому выдавал 94 и 41, а
`forgeplan-brownfield-pack:discover` — реальный forgeplan-aware агент — не попадал ни в одно
публикуемое число.

> **Закрыто в #229.** Счётчик научен спускаться на уровень ниже и отличать агента от соседнего
> README по наличию `name:` во frontmatter; заодно он теперь следует по символическим ссылкам
> (`readdirSync` их не разворачивает, и симлинк-агент проваливался мимо обеих веток) и не считает
> агентом файл, у которого `name:` пустой. Опубликованные числа приведены к 95 и 42.

## 6. Санитария процесса

| Что | Состояние |
|---|---|
| `forgeplan health` | `needs_attention`, 365 артефактов, **9 stale drafts** |
| Черновики | PRD-077, PRD-078, SPEC-004, RFC-024, ADR-021 + EVID-204..207 |
| EVID за смёрженную работу сессии | **ноль** |

Пять из девяти черновиков — артефакты этой сессии: заведены, но не проведены через гейт и не
активированы. Ни одного EVID за семь смёрженных PR не создано. То есть работа сделана, а
доказательной цепочки под ней нет — ровно то состояние, которое сам конвейер и должен ловить.

Это не отдельный дефект, а следствие §1.2 и §1.1 вместе: цикл не двигает фазу, гейта нет,
значит ничто не напоминает о незакрытом хвосте.

## Как перепроверить

Карта состоит из чисел, значит проверяется пересчётом. Расхождение означает, что врёт карта.

```bash
cd forgeplan-marketplace

# §7 — агенты
find plugins/*/agents -name '*.md' -type f | wc -l                       # 97 файлов
find plugins/*/agents -maxdepth 1 -name '*.md' -type f | wc -l           # 94 — верхний уровень
node scripts/ci/catalog-check.js | grep agents                            # 95 — столько считает гейт
# настоящих агентов 95: 97 минус discover/README.md и discover/SCAFFOLDING.md (см. §5.1)
grep -l '^disallowedTools:' plugins/*/agents/*.md plugins/*/agents/*/*.md | wc -l   # 42

# §5 — карточки методологий
awk '/^## Methodology cards/{f=1;next} /^## /{if(f)exit} f&&/^### /{c++} END{print c+0}' \
  plugins/fpl-skills/skills/smith/routing-map.md                          # 33
grep -c '^### ' plugins/fpl-skills/skills/smith/routing-map.md            # 39 (все ###, не только карточки)

# §2 — покрытие NFR
cd ../.forgeplan/prds && ls *.md | wc -l && grep -lE '^## Non-Functional' *.md | wc -l   # 79 / 29
grep -lE '\| *Metric *\| *Condition *\| *Measurement *\|' *.md | wc -l    # 19
cd ../../forgeplan-marketplace

# §2 — правил NFR в бинаре нет
strings $(which forgeplan) | grep -oE '\bprd-[a-z-]+' | sort -u | grep -i nfr   # пусто

# §1.2 — фазовый слой

for t in "story map" "impact mapping" "wardley" "opportunity solution tree"; do
  echo -n "$t: "; grep -ril "$t" plugins/ docs/ | wc -l; done                   # все 0

# §4 — что видит guardian
grep -oiE '(C4|ADI|BMAD|delta-spec|ground-truth|DDD|STRIDE|NFR)' \
  plugins/agents-pro/agents/guardian.md | sort | uniq -c

forgeplan health --json | python3 -c \
```

## Что в карту не входит

- **Оценка качества техник.** Уровень T1–T4 говорит про удержание дисциплины, а не про то,
  хороша ли техника.
- **Production observability.** `docs/AI-SDLC-MAPPING.md:39` объявляет это вне области —
  карта уважает это решение, а не считает дырой.
- **Английская версия.** Карта рабочая и внутренняя; если понадобится вынести наружу, тогда и
  переводить.
