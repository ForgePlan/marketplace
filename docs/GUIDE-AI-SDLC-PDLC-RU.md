# Гайд: как вести разработку с агентами — AI-PDLC и AI-SDLC

Настольная книга по тому, что у нас построено: две петли (продуктовая и инженерная), кто в них
играет, в каком порядке, где стоят гейты, кто кого проверяет, как задача находит свою методологию,
и какой модели какую задачу отдавать.

Всё, что здесь про механику, снято с диска 2026-09-04. Где стадия или роль не построена — так и
написано, а не описано намерение. Где утверждение не замерено — стоит явная пометка.

**Этот гайд не заменяет, а сшивает:**

| Документ | Что в нём |
|---|---|
| [`GUIDE-PIPELINE.md`](GUIDE-PIPELINE.md) | канонический конвейер: 11 стадий, три гейта, три входа |
| [`SMITH-RU.md`](SMITH-RU.md) | роутер методологий, 14 строк |
| [`METHODOLOGIES-RU.md`](METHODOLOGIES-RU.md) | 33 карточки методологий |
| [`../plugins/fpl-skills/AGENT-AUTHORING-GUIDE.md`](../plugins/fpl-skills/AGENT-AUTHORING-GUIDE.md) | канон профилей агентов, дисциплины ревьюеров, ground-truth |
| [`FACTORY-RU.md`](FACTORY-RU.md) | зачем это всё одной фразой |

---

## 0. Одной страницей

**Формула.** Мы строим фабрику, которая умеет строить, проверять саму себя и честно записывать,
где она ошиблась.

**Две петли.**

```
AI-PDLC  ──►  что строить      ──►  PRD (активный)
                                      │
AI-SDLC  ◄────────────────────────────┘  ──►  код + доказательства + активированный артефакт
```

Шов между ними один и он узкий: **PDLC отдаёт активный PRD, SDLC его потребляет**. Тот же самый
артефакт, не пересказ. Это единственное место, где две петли соприкасаются, и поэтому единственное
место, которое надо охранять.

**Три вещи, которые делают эту конструкцию не декорацией:**

1. **Генератор ≠ верификатор.** Никто не проверяет собственную работу. Проверяющий не верит отчёту
   исполнителя — он сам читает замороженную внешнюю истину (git, тело артефакта).
2. **Профиль роли — это денилист инструментов, а не описание.** Ревьюер физически не может
   активировать то, что отревьюил.
3. **Гейт, который блокирует всё, обходят `--force` на первом же ложном срабатывании.** Поэтому
   блокирует только структурное; спорное — сообщается.

# Часть I. Продуктовая петля (AI-PDLC)

## 1.1 Решение и что оно чинило

Решение — **ADR-023**. Проблема была не в том, что нет техник продуктового открытия: на машине уже
стояли 68 SKILL.md стороннего pm-маркетплейса, покрывающих OST, интервью, персоны, сегментацию,
метрики — и **ни одной ссылки на forgeplan во всех 68**.

Дыра была в другом: **у результата открытия не было места в графе**. Вид PROBLEM за всё время
использовался дважды, оба раза инженерно-внутренне; четыре нативных инструмента открытия не вызывал
никто.

Поэтому PDLC у нас — это не «поставить ещё карточек с методиками», а **мост**: сделать так, чтобы
продуктовое открытие приземлялось в тот же граф решений, что и инженерия.

## 1.2 Вход и проход

Вход: **`/discover-product`** (плюс саб-моды `jtbd` и `assumptions`).

Проход — Double Diamond, шесть шагов:

| Шаг | Что происходит | Что рождается |
|---|---|---|
| 0. Orient | `test -d .forgeplan` — жёсткий стоп, если workspace нет; определяем MCP или CLI | — |
| 1. Discover (расхождение) | «Какой продуктовый вопрос? Что заставило подумать об этом сейчас?» Можно диспатчить `research-analyst` (Profile C, read-only) — но **персистит скилл/оркестратор, не агент** | discovery NOTE с прикреплёнными источниками |
| 2. Define (схождение) | «Одним предложением: что сломано, чего не хватает, и для кого?» | **PROBLEM** — по одной на подтверждённую проблему, ДО всякого PRD |
| 3. Гейт C4 | `artifact-reviewer` (Profile B) ревьюит NOTE + PROBLEM вместе | EVID с PASS/CONCERNS/BLOCKER |
| 4. Develop (расхождение) | «Что должно быть правдой? Самое рискованное первым» | **HYPOTHESIS**-артефакты, двигаются `parked → inferred → strong-inferred → verified \| refuted` |
| 5. Deliver (схождение) | Формулировка задачи как JTBD: «Когда [ситуация], я хочу [мотивация], чтобы [результат]» | **PRD** с непустыми Non-Goals |

Дальше — `architect-reviewer` на пригодность PRD и `guardian` перед активацией.

## 1.3 Три правила честности (их нельзя автоматизировать, поэтому они написаны)

1. **Не изготавливай подтверждённую проблему из одного интервью.** Минимальная планка для PROBLEM —
   **≥2 независимых источника** (интервью, сигнал в данных, тикеты поддержки — не два человека,
   пересказывающих один анекдот). Иначе в теле PROBLEM висит видимая метка
   `**Status**: assumption, unvalidated`.
2. **Эксперимент или интервью, результат которого не записан, не состоялся.** Вернись и запиши, а не
   восстанавливай по памяти.
3. **Гипотеза стоит в своём настоящем состоянии.** Не продвигай в `verified`, чтобы проход выглядел
   дальше продвинутым. `hypothesis_status` — это лог, который никто не переписывает.

## 1.4 Что сознательно деградировано

`forgeplan_interview_packet_draft` и `_ingest` — **заглушки** в работающем ядре 0.34.0: их
собственные описания схемы содержат слово STUB и всегда возвращают `not_implemented`. Скилл **не
имеет права их звать** (инвариант INV-6: инструмент, вызванный ради счётчика, хуже отказа с
причиной).

Причина — **пространство имён, а не отсутствие возможности**: плагин может нести собственный
MCP-сервер (fpl-hsmem несёт), но публикуется под своим namespace и никогда не закроет
`mcp__forgeplan__*`, которые ядро уже зарезервировало заглушками. Замена — путь через discovery
NOTE: тот же результат (сохранённая, связанная, с источниками запись интервью) минус структурные
предложения HYP/UC/INV, которые пакет должен был выводить из транскрипта. Трекер: marketplace#265.

## 1.5 Живое состояние петли

На 2026-09-04: гипотез в графе — ноль, PROBLEM — две, обе инженерно-внутренние. **Ни один
продуктовый цикл через новую петлю ещё не прошёл.** ADR-023 стоит с R_eff 0.00 — по построению:
подтверждение сработает после первого настоящего цикла, не раньше.

Это записано, а не спрятано: гайд, который читается как сертификат готовности, — худший вид гайда.

# Часть II. Инженерная петля (AI-SDLC)

## 2.1 Одиннадцать стадий

Носитель счёта — `plugins/fpl-skills/templates/project-agent-matrix.yaml`. Ни один документ не
пересчитывает их руками; `scripts/ci/phase-canon-check.js` роняет CI на любой попытке.

| Стадия | Что происходит | Методология | Шаг `/forge-cycle` |
|---|---|---|---|
| `brief` | сырая идея → структурированный Brief | — | 2.5 (`brief-intake`, только если задача пришла сырой) |
| `shape` | Brief → PRD | BMAD | 4 |
| `decompose` | PRD → братские RFC | FPF | 4.4 (`goal-planner` + `forgeplan_decompose`, Deep+) |
| `design` | RFC — технический контракт | SPARC Architecture | 4 + 5; 4.5–4.6 добавляют ADI и красные линии |
| `estimate` | трудозатраты и риск; **записывает глубину**, которую применит гейт | — | 4.65a (глубина всегда) + 4.65b (`/estimate`, Deep+) |
| `gate` | **можно ли переходить к сборке?** | — | 4.7 (`/gate-check`) |
| `build` | код | SPARC Refinement / RIPER | 5 |
| `audit` | многоревьюерный проход | FPF / BMAD | 6.5 + 6.6 |
| `evidence` | EVID создан и связан | — | 7, пост-сборочный гейт на 7.4 |
| `activate` | финальный гейт, потом активация | — | 7.5–8 (`guardian`) |
| `wrap` | сверка, потом REFRESH на Deep+ | ADR-020 | 10 (`/wrap`) |

Все одиннадцать сегодня исполняются. `brief` и `decompose` подключены последними (2026-09-04): у
обеих агент был с самого начала и не было ничего, что бы его вызывало.

**Условные под-ступени** — не стадии, они висят на именованной стадии и срабатывают только на своей
ветке: Epic (на `brief`), Diagnose и Solution portfolio (bug-fix ветка), SPEC и ADR (на `design`),
пост-сборочный гейт (на `evidence`, Deep+), ship (после коммита, Standard+).

## 2.2 Три входа — они не взаимозаменяемы

| Вход | Роль |
|---|---|
| `/forge-cycle` | реактивный — зовёшь на задачу; останавливается и спрашивает на конфликтах |
| `/autorun` | автономный — брифуется вперёд, потом идёт часами, разрешает конфликты через FPF. **Никогда не делает `--force`**: обход гейта, причину которого некому прочитать, — это гейт, который не работал |
| `forgeplan playbook run` | декларативный — YAML-воркфлоу под домен. **Работает, но через него ничего не поставляется** — эталонных плейбуков нет (#237) |

`/autorun` — это **не** «`/forge-cycle` без вопросов». Они различаются политикой решений, а не
намерением (ADR-005), и **не ходят по одинаковым стадиям**: на собственном пути `/autorun` идёт
`research → sprint → audit → report`, где нет ни `shape`, ни `design`. Гейт при этом вызывается до
того, как `sprint` что-либо задиспатчит — то есть переход, который защищает RFC-002 INV-1, покрыт на
обоих путях. Паритет стадий — нет.

## 2.3 Глубина решает, насколько строго

| Глубина | Артефакты | ADI | Обязательный минимум гейта |
|---|---|:---:|---|
| **Tactical** | ничего или NOTE | — | `validate` чист |
| **Standard** | PRD → RFC | желательно | `validate` чист |
| **Deep** | PRD → SPEC → RFC → ADR | **обязателен** | + ADI-доказательство (≥3 гипотезы в связанном EVID) |
| **Critical** | Epic → PRD[] → SPEC[] → RFC[] → ADR[] | **обязателен + ревью** | + связанный активный ADR |

**Глубина записывается, а не предполагается — и не эскалируется без человека.** `forgeplan get`
возвращает `standard` для любого артефакта любого вида (отражённый `default_depth`), поэтому шаг
4.65 гоняет `calibrate` и записывает настоящую. Тот же замер показал, что `calibrate` предлагает
Deep для 4 из 4 прозондированных артефактов — поэтому шаг **спрашивает** перед эскалацией, а
`/autorun` сохраняет существующую глубину: поднять уровень без человека — это автономный эквивалент
`--force`.

# Часть III. Роли и разделение контекстов

## 3.1 Семь профилей

Профиль — это не описание в шапке, это **денилист инструментов**. Ниже — канонические формы, снятые
с диска.

| Профиль | Может | Не может (денилист) | Кто это на диске |
|---|---|---|---|
| **A** Создатель | создавать артефакты (`forgeplan_generate` первично, `forgeplan_new` резервно), update, link, validate, **reason** (ADI — контракт профиля A), claim/release, memory_retain | `Write`, `Edit`, `NotebookEdit`, `forgeplan_activate` — **ровно 4 записи** | adr-architect, artifact-author, brief-intake, goal-planner, architecture, specification, tdd-planner |
| **B** Ревьюер + автор EVID | читать код и артефакты, гонять Bash-линтеры и тесты, создать EVIDENCE, update тела, link informs, validate, score, claim **ровно одного** артефакта | те же 4 + `forgeplan_reason` (ADI принадлежит A) + `forgeplan_claims` (без разведки соседей) + `memory_retain` — **ровно 7** | code-reviewer, tester, security-expert, architect-reviewer, artifact-reviewer, system-dev, evidence-recorder |
| **B-gate** | всё то же + выносит бинарный вердикт по всей цепочке доказательств | та же семёрка, что у B (у guardian запрет активации исторически отсутствовал во фронтматтере при трёх запретах в теле — приведён к канону в v1.21.0; tdd-test-validator короче на две записи: не запрещает `forgeplan_claims` и `memory_retain` — известное отклонение) | guardian, tdd-test-validator |
| **B-orchestrator** | читать широкое состояние, диспатчить через Task, держать гейты | всё вышеперечисленное **плюс** Bash и все forgeplan-мутации — **16 записей** | smith, bmad-orchestrator, sparc-orchestrator, tdd-orchestrator, canvas-coordinator, map-orchestrator |
| **C** Read-only | читать, искать, синтезировать → возвращает оркестратору | **все** мутации — 17 записей | research-analyst |
| **C-coder** | `Write`/`Edit`/`Bash` по исходникам — **единственный, кому это можно** | все forgeplan-мутации | coder, coder-tdd, canvas-coder |
| **D** Сопровождающий | чинить существующие артефакты на месте | + `forgeplan_new` (не создаёт нового) | artifact-maintainer |

**Правило, которое из этого следует и которое ловит людей:** Profile B физически не может
активировать то, что отревьюил. Поэтому EVID после ревьюера остаются в `draft`, и это **не баг** —
это спроектированное следствие разделения. Разрешается оркестратором: ревьюер эмитит сентинел
`<<NEEDS_ACTIVATION>>`, активирует оркестратор.

## 3.2 Четыре механизма принуждения — и где они врут

| Механизм | Сила | Ограничение |
|---|---|---|
| `disallowedTools` денилист | стена | **только Claude Code.** В рантайме без этого ключа это ничто, и ошибка не поднимается |
| `tools:` аллоулист | **жёстче денилиста** | но аллоулист без единого forgeplan-инструмента делает агента неспособным записать EVID, который от него требует маршрут |
| HARD RULES в теле агента | переносимо между CLI | социальная дисциплина, не стена |
| Линт LR-1..LR-8 в `validate-all-plugins.sh` | ловит расхождение канона | проверяет то, что заспецифицировано |

**Отсюда инвариант:** всё, что защищает денилист и что действительно важно, **обязано** быть ещё и
HARD RULE в теле. 42 агента маркетплейса несут денилист, и каждый запрещает `forgeplan_activate`; в
Gemini CLI / Codex CLI / Goose это не значит ничего. Тихий отказ назван явно: Profile B активирует
артефакт, который сам же отревьюил, генератор ≠ верификатор рушится, и никто об этом не сообщает
(marketplace#218).

## 3.3 Генератор ≠ верификатор: корневой принцип

Цепочка происхождения: **PROB-002** (инцидент: исполнитель отчитался об успехе, вниз по течению
поверили отчёту, разрыв всплыл позже) → **RFC-011** (архитектура, FR-3) → **ADR-009** (решение).

Четыре правила:

1. **Проверяй побочный эффект, а не самоотчёт.** Для кода истина — объектное хранилище git
   (`git diff base..head` в чистой оболочке). Для мутации артефакта — сохранённое тело
   (`forgeplan_get`, убедиться, что заявленная секция действительно там). Транскрипт исполнителя
   («готово», «тесты прошли») — дополнение, не доказательство.
2. **Пустой diff при зелёных тестах = BLOCKER.** Зелёный набор тестов при пустом diff — это нулевой
   результат, а не пропуск: набор остаётся зелёным, когда ничего не менялось. Держится даже при
   чистых сканерах.
3. **Герметичная оболочка и настоящий корень репозитория для каждого зонда git.** `bash --noprofile
   --norc`, корень через `git -C <cwd> rev-parse --show-toplevel`. Никогда не предполагай, что
   `$CLAUDE_PROJECT_DIR` — это git-репозиторий (здесь корень workspace им не является, репозиторий
   маркетплейса — дочерняя папка).
4. **Ревьюер вставляет доказательство, гейт его перепроверяет.** Profile B пишет буквальные команды
   и вывод в секцию `## Ground-truth verification`. Guardian блокирует любой EVID, заявляющий
   изменение кода, если секции нет или в ней `DELTA=EMPTY`.

### Таблица пола вердикта (шаг 4.5)

Применяется **до** категоризации находок:

| Состояние | Пол вердикта |
|---|---|
| DELTA=EMPTY + любой токен | **BLOCKER** — «разрыв заявления и реальности» |
| DELTA=PRESENT + выводимый токен ABSENT | **CONCERNS** — «возможно неверное или частичное изменение» |
| DELTA=PRESENT + FOUND либо токен невыводим | предусловие выполнено, PASS допустим |
| база не разрешается | максимум CONCERNS, **никогда** PASS |

Ключевая деталь ADR-009: **ожидаемый токен изменения пишет планировщик**, в acceptance criteria
PRD/SPEC (поле `expected_delta:`), и он инжектится вниз и в шаблон коммита исполнителя, и в проверку
гейта. Вариант «исполнитель пишет его сам» отвергнут явно как генератор==верификатор: исполнитель
напишет тривиальный regex, которому удовлетворяет любое изменение. Мотивация — ImpossibleBench:
фронтирные модели взламывают видимые тесты в 54–93% случаев.

### Граница между структурным гейтом и семантическим ревью

- «Приземлилась ли **какая-то** заявленная дельта и трогает ли она объявленный токен?» → жёсткий
  автоматический гейт, exit 2, принуждается харнессом.
- «Это **правильное** изменение?» → Profile B ревьюер, **никогда** не regex по прозе.

Хуки остаются тупыми-но-необходимыми, суждение уходит независимому ревьюеру.

## 3.4 Разделение контекстов — практические правила

- **Свежий изолированный контекст на каждый диспатч.** И генератор, и верификатор. Это и делает
  генератор ≠ верификатор настоящим: верификатор не наследует допущений генератора.
- **Переклеить ярлык роли на тот же контекст — не верификация.** ADR-010 C4 определяет «другой
  контекст» узко: отдельный диспатч без общего изменяемого рабочего состояния с производителем.
- **Цепочки гейтов остаются последовательными.** Генератор и его верификатор **никогда** не гоняются
  параллельно; порядок кодируется через `blockedBy`, а не подразумевается порядком диспатча.
- **Изоляция worktree работает и она не только для coder** — обычные сабагенты, прогоны Workflow и
  участники AgentTeams получают изолированные worktree (проверено на 14 штуках в живом проекте).
  Только *объявление* `isolation: worktree` во фронтматтере специфично для coder.
- **Но изоляция различается по виду писателя.** Параллельные писатели **кода** получают свой
  worktree. А писатели **документации** идут без worktree, на ветке: doc-писатель, задиспатченный в
  изолированный worktree, пишет мимо рабочей ветки, и изменение молча не приземляется туда, где его
  ждёт оркестратор. Doc-писатели держатся без гонок за счёт строгого владения файлами: писатель
  правит, **оркестратор** стейджит и коммитит.
- **Строгое владение файлами.** Параллельный веер безопасен только там, где работа файлово-непересекающаяся.
  Если два юнита трогают один файл — они не братья, их надо выстроить через `blockedBy`.
- **Шаг 9c: проверка файловой системы после каждого заявления.** После каждого диспатча C-coder,
  заявляющего изменения файлов, оркестратор **обязан** сделать grep по диску. Возвраты сабагентов
  ненадёжны **в обе стороны**: один вернул «12 файлов изменено, ВСЁ ПРОШЛО», когда 0 из 8 агентов
  получили поле; другой доложил «0 найдено, изменений нет», хотя удаление на самом деле выполнил.

## 3.5 Гигиена claim

| Профиль | Может claim? |
|---|---|
| A | да — один артефакт, который создаёт |
| B ревьюер | да — ровно один артефакт, который ревьюит (`forgeplan_claims` запрещён) |
| B-orchestrator | **нет** — читает широко, не мутирует ничего |
| C read-only | **нет** — исследователь, которому кажется, что нужен claim, неверно профилирован |
| D | да — один артефакт, который чинит |

**HARD RULE 10: release — это `finally`, а не хвост счастливого пути.** С момента вызова
`forgeplan_claim` агент должен release при PASS, CONCERNS, BLOCKER, провале валидации, падении
анализатора и любом обрыве после claim. Живой инцидент: три read-only ревьюера заявили claim на
RFC-008/009/010, упали до release, оставили `active_claim_count: 3` и отправили все три в
последовательную очередь. Два отказа сложились: ревьюеры **не должны были** claim'ать, и оркестратор
**не подмёл**. Чинится обе половины.

# Часть IV. Гейты — что и кого может остановить

## 4.1 Четыре слоя гейтов

| Слой | Кто | Вопрос | Что роняет |
|---|---|---|---|
| Между стадиями | `/gate-check` | можно ли на следующую стадию? | пороги `quality-gates.yaml` |
| После сборки | `/gate-check --post-build` | сборка соответствует спеке? | пороги + рост доказательств (Deep+) |
| Перед активацией | `guardian` (агент) | это можно активировать? | вся цепочка доказательств |
| Репозиторий | 13 CI-гейтов + 5 хуков + защита веток | это можно вливать? | структура, безопасность, паритет |

`guardian` — строже и позже. **PASS от `/gate-check` не даёт права его пропустить.**

## 4.2 Пороги: что блокирует, а что сообщается

```yaml
pre_build.tactical:  must: validate_errors_max: 0
pre_build.standard:  must: validate_errors_max: 0
pre_build.deep:      must: validate_errors_max: 0 + adi_evidence_required
pre_build.critical:  must: + adr_linked_required
```

**Каждый must — структурный. Ничего, выведенного из `score`, не блокирует.** Это замерено, а не
робость.

`must` — это то, что читатель решает без спора: секция MUST есть или её нет; связанный EVID несёт
три гипотезы или не несёт; активный ADR информирует этот артефакт или ни один не информирует. Каждый
называет то, что автор сделал или не сделал, и у каждого очевидное исправление.

Оценки пробовали как must, и каждая провалила замер (14–16 живых артефактов, 2026-09-03):

- **`r_eff` — это минимум по графу, который движется не в ту сторону.** PRD-024 упал 1.00 → 0.30
  **потому что его отревьюили**: честный аудит пришёл с `weakens`, набрал 0.5 и стал минимумом.
  Блокировать по нему — значит валить артефакт за то, что он записал неблагоприятное свидетельство о
  себе.
- **`granularity` зависит от вида, а не от качества.** ADR кучкуются на 0.20–0.40, PRD и EPIC на
  0.80–1.00. ADR — это одно решение; низкая гранулярность для него правильна.
- **`formality` выглядела пригодной и не является.** Порог 0.6 пропускает все 16 отобранных
  активированных артефактов, но самый низкий, ADR-006 на 0.38, — структурно полный семисекционный
  MADR.

Ранний черновик сделал `r_eff`, `granularity` и `reliability` must'ами на Deep. На 16 артефактах это
заблокировало **56%** — включая сам PRD-024, RFC-002 (источник инварианта, который этот гейт
принуждает) и ADR-022, который проект только что провёл полным циклом до PASS от guardian. Бюджет
ложных срабатываний — NFR-003 PRD-024 — ≤5%. **Гейт, который блокирует половину уже принятой
работы, не строгий — он сломанный, и его `--force`нут при первом же срабатывании.** Текущий набор
блокирует 0% той выборки.

## 4.3 Guardian: как выводится вердикт

Базовая таблица из трёх строк, «без исключений, без мягкости суждения»:

- любой неразрешённый BLOCKER в любом связанном EVID, или сигнал конфигурации проекта → **BLOCKER**
- BLOCKER'а нет, но есть неразрешённые CONCERNS высокой важности, пропущенная или проваленная
  валидация, невыполненная политика активации → **CONCERNS**
- всё зелёное → **PASS**

Поверх — **22 строки модификаторов вердикта**. Самые нагруженные:

| Строка | Что ловит | Вердикт |
|---|---|---|
| нет проходящего Profile B аудита | ноль EVID ревьюера | BLOCKER |
| цепочка доказательств пуста | активация без свидетельств | BLOCKER |
| дисциплина FPF ADI отсутствует | <3 гипотезы на Standard+ | BLOCKER |
| дисциплина ground-truth (ML-13) | EVID заявляет изменение кода без секции проверки или с DELTA=EMPTY | BLOCKER |
| связанный ADR со сработавшим Revisit Trigger | решение просрочено | BLOCKER |
| BMAD: ноль находок на Standard+ | ревьюер был недостаточно адверсариален | CONCERNS |
| дисциплина открытия (ADR-023 D4) | Standard+ PRD с пустыми Non-Goals или без пользовательской работы | CONCERNS |
| C4-диаграммы для решений на ≥3 модуля | межмодульный поток в прозе без диаграммы | CONCERNS |
| дельта-спека OpenSpec отсутствует при supersede | история supersede теряет контекст | CONCERNS |
| дисциплины NFR / DDD / STRIDE | по образцу строки C4 | CONCERNS |

Плюс два HARD RULE, которые не про содержание: **понижение по радиусу поражения** и **никакого
штампа под давлением сроков**.

## 4.4 Обход

`--force` требует `--reason`, записывает NOTE с перечнем **каких именно** проверок обошли и их
замеренных значений, возвращает PASS с меткой `overridden`. **Сознательно не отключаемый:** гейт,
который никто не может пройти в аварии, — это гейт, который в аварии удалят. Сделать аварийный люк
громким долговечнее, чем заварить его.

С версии 1.19.0 guardian **читает** NOTE с заголовком `Gate override:` — до этого обход записывался
и никем не читался, то есть был почти бесплатным.

## 4.5 Пять fail-closed хуков

| Хук | Что делает |
|---|---|
| `tdd-gate.sh` | фаза `tdd-plan` запрещает запись и в исходники, и в тесты; `tdd-red` разрешает тесты и запрещает исходники без маркера `STUB:TDD`; GREEN **блокирует любую правку теста** и блокирует запись исходника, если живой хеш SPEC разошёлся с замороженным |
| `bmad-gate.sh` | нет кода до утверждённого плана |
| `canvas-gate.sh` | нет записи в исходники дизайн-системы, пока tokens RFC не активен |
| `safety-hook.sh` | денилист Bash: force-push, прямой push в main/dev, `reset --hard`, `clean -fd`, `rm -rf /`, DROP TABLE |
| `commit-delta-gate.sh` | коммит с трейлером `Expected-delta: <regex>` обязан дать непустой staged diff, добавленные строки которого совпадают с regex, иначе exit 2 |

Все блокируют через `permissionDecision:deny`; при непарсящемся вводе — **exit 2, никогда не
«разрешить»**. Хук сессионно-глобальный, поэтому связывает и сабагентов, и **правки человека мимо
конвейера**, до которых оркестратор, работающий только диспатчем, не дотягивается.

## 5.2 Контракт под-цикла (ADR-010): C1–C6

Пять методологий построены как **под-циклы** по одному контракту. Это и есть ответ на вопрос «как
роль знает, где остановиться».

| Элемент | Что это |
|---|---|
| **C1** Вход | под-цикл стартует, только если входные артефакты `active`; мастер отказывается иначе |

| **C4** Независимый верификатор | **другой** контекст сертифицирует продукт до выхода. FAIL → назад в производящую фазу; PASS → продукт **замораживается** |

| **C6** Выход | EVIDENCE, который **обязан** нести вердикт C4 (`PASS`) и **личность верификатора**. Следующая стадия открывается только по PASS из контекста, отличного от C3 — не по факту существования EVIDENCE |

**Условная заморозка:** для фаз без замораживаемого продукта (исследовательская проза, эволюционирующая
модель) C4 всё равно сертифицирует, а C6 записывает, но заморозка не применяется — вместо неё C6
**пинит отревьюенную ревизию**. Живых экземпляра два: Research NOTE в RIPER и Design NOTE в CANVAS.

### Тест хук-гейта (ADR-012) — почему не у всех методологий есть свой мастер

> **Требует ли эта методология fail-closed PreToolUse хука, который связывает правки, недостижимые
> дисциплиной диспатча мастера?**

- **ДА** → выделенный B-orchestrator + свой хук + state-lib + фазовые агенты (уровень 3).
- **НЕТ** → «мастер» — это `/skill` + строка в карте роутинга + главная сессия, оркестрирующая
  существующих агентов (уровень 1/2), а дисциплину гейтов несут верификаторы C4 + шаги 4.5/6.5
  `/forge-cycle` + guardian.

Тест выбран специально потому, что **проверяется по диску** (файл хука либо есть и запрещает, либо
нет), а не семантически, как G5/G6/G7.

Популяция мастеров ограничена: 1 общий (smith) + не больше 2–3 узких — задокументированная линия
запаха. Сейчас 1 + 5.

# Часть VI. Ярусы моделей — какую задачу кому отдавать

Это единственная часть гайда, которой ещё нет ни в одном артефакте маркетплейса. Помечаю
происхождение каждого утверждения явно, потому что половина ценности здесь — в том, что видно, где
замер, а где чтение из сети.

## 6.1 Две лестницы, а не одна

Просится одна лестница из девяти ярусов (A/A+/A++, B/B+/B++, C/C+/C++). Но задача и модель — разные
вещи, и нумеровать их одной шкалой — инфляция ярусов. Поэтому две разные лестницы:

| Лестница | Что нумерует | Сколько рунгов | Статус |
|---|---|:---:|---|
| **Ярус задачи** | свойство **работы**: цена ошибки × обратимость × наличие внешнего оракула | **9** | предложение, ниже |
| **Ярус модели** | какая модель обслуживает | меньше (у нас — 6) | живёт в конфигурации конкретной машины, вне этого репозитория |

**Отображение — многие-к-одному, и это и есть главная мысль:**

> Плюс в ярусе **задачи** чаще всего покупает **обвязку**, а не более крупную модель: второй проход,
> независимого верификатора, гейт, человека в петле.

Слабая модель на хорошей постановке даёт больше, чем сильная на «сделай красиво». Наш граф решений
это косвенно подтверждает: доказательств в нём в два с половиной раза больше, чем постановок задач —
работа уходит в проверку, а не в генерацию.

## 6.2 Девять ярусов задачи

Ярус определяется тремя измеримыми признаками, а не «сложностью» на глаз:

1. **Цена ошибки** — что сломается и как быстро заметим.
2. **Обратимость** — откатывается одной командой или переписыванием истории.
3. **Внешний оракул** — есть тест/гейт/замер, или только суждение.

Первые два задают букву, третий — плюсы.

| Ярус | Что это за задача | Обвязка, которую покупает плюс | Ярус модели |
|---|---|---|:---:|
| **C** | Механика с оракулом: переименования, форматирование, codemod под тесты | — (проверка = линтер и тесты) | C |
| **C+** | Механика **без** оракула: синхронизация доков, счётчиков, версий | обязательный второй проход на сверку | C, сверка — B |
| **C++** | Массовые однотипные правки по многим файлам | по одному изолированному вызову на файл + строгое владение файлами | C ×N |
| **B** | Понятная фича в знакомом коде, тесты есть | гейт закрывает | B / B+ |
| **B+** | Фича, где надо выбрать между двумя реализациями | независимый ревьюер **сильнее автора** | B+ автор, A ревьюер |
| **B++** | Отладка живой проблемы, причина неизвестна | сильная на диагностику, средняя на починку | A диагноз, B+ починка |
| **A** | Проектирование контракта, схемы, границ | результат обязан пройти **чужой** гейт | A |
| **A+** | Архитектурное решение с альтернативами и последствиями | обязательный цикл ADI (≥3 гипотезы) + гейт | A+ |
| **A++** | Необратимое: миграция данных, публичный контракт, безопасность | генератор ≠ верификатор, **человек в петле**, откат описан заранее | A++ |

**Тест яруса**: *для каждого яруса назови задачу, которая принадлежит ему и была бы неправильной
ярусом выше или ниже. Если эту фразу трудно написать — ярус декоративен.*

И следствие: **если два яруса отправляют одинаковую работу моделям одного класса — это один ярус с
двумя именами.**

## 6.3 Лестница моделей — правила, не список

Конкретный список «какая модель стоит за каким ярусом» — это конфигурация конкретной машины и
подписок, она **не живёт в этом репозитории** (и не должна: она меняется чаще, чем любой документ
здесь, и раскрывает чужой стек). Здесь живут правила, по которым такой список собирается:

1. **Ярус просит агент, модель за ярусом выбирается один раз.** Агент знает, насколько трудна его
   задача; какая модель обслуживает ярус — отдельное решение уровня конфигурации, не уровня вызова.
2. **Соседние верхние ярусы могут быть одной моделью на двух усилиях.** Плюс — это глубина
   размышления, а не другой вендор. Но суффикс усилия работает только у моделей, которые сообщают
   управляемое усилие; на модели без него он **молча отбрасывается** — ручка, которую молча
   игнорируют, читается как работающая ручка. Проверяй, что модель усилие принимает, прежде чем
   строить на нём ярус.
3. **Модель со счётчиком (оплата за токен) никогда не становится основной для яруса, пока в том же
   классе есть модель на фиксированном плане.** Счётчик тратит реальные деньги, план — квоту.
4. **Модель со счётчиком — правильное ПОСЛЕДНЕЕ звено цепочки** (когда план упёрся в стену квоты) и
   ставится в конфигурацию выключенной. Включается решением, а не по умолчанию.

## 6.5 Правила маршрутизации — коротко

1. **Ярус выбирает задача, а не агент.** Агент просит ярус, потому что знает, насколько трудна его
   работа. Какая модель стоит за ярусом — отдельное решение, принятое один раз.
2. **Верификатор никогда не слабее генератора.** Ревьюер на ярусе ниже автора — это штамп, а не
   ревью.
3. **Ярус модели не спасает плохую постановку.** Если задача сформулирована как «сделай красиво» —
   поднимать ярус бессмысленно, надо возвращаться на `shape`.
4. **Массовая работа (C++) идёт по одному изолированному вызову на файл**, а не одним вызовом на
   пачку — иначе теряется владение файлами и падает изоляция контекстов.
5. **A++ никогда не идёт без человека в петле** — независимо от того, насколько хороша модель.

## 6.6 Что здесь не замерено (открытый вопрос с триггером)

Отображение «ярус задачи → ярус модели» **у нас не проверено экспериментом**. Правильный способ
проверить: прогнать один класс задач на двух соседних ярусах и сравнить **долю находок ревьюера** —
если она не меняется, соседние ярусы схлопываются в один.

**Revisit Trigger:** после первого цикла, где ярус выбирался осознанно, — замерить и либо схлопнуть
лестницу, либо подтвердить девять рунгов числом.

## 7.1 Ярлыки профилей, не подкреплённые фронтматтером

## 7.2 Две строки маршрутизации требовали невыполнимого — починено 2026-09-05

Дефект (найден аудитом): строки 8 (безопасность) и 9 (производительность) требовали EVID от
`injection-analyst`, `pii-detector` и `performance-engineer`, чьи аллоулисты
`[Read, Bash, Glob, Grep]` не содержали **ни одного** forgeplan-инструмента — записать требуемое
доказательство эти агенты структурно не могли. Удаление Write/Edit (marketplace#236) починило
половину «ревьюер может править», но оставило половину «не может записать».

`memory_retain` запрещены пропуском из аллоулиста, а переносимые HARD RULES дисциплины EVID
(две оси вердиктов, честный ноль как CONCERNS, сентинел `<<NEEDS_ACTIVATION>>`, release как
`finally`) добавлены в тела. `performance-engineer` дополнительно привязан к шаблону
`perf-baseline.md` — базовый EVID с p50/p95/p99 и командой воспроизведения обязан появиться
**до** любого изменения.

# Часть VIII. Шпаргалка

## Что запускать

```bash
# не знаю, что делать дальше
/smith

# знаю задачу, не знаю методологию
/smith-plan "<задача>"

# что строить (продуктовая петля)
/discover-product                    # полный проход Double Diamond
/discover-product jtbd PROB-NNN      # только формулировка работы
/discover-product assumptions PROB-NNN  # только карта допущений

# строить (инженерная петля)
/forge-cycle "<задача>"              # реактивно, спрашивает на конфликтах
/autorun                             # автономно, часами, без --force

# по методологиям
/bmad        # greenfield
/sparc       # фича в существующем сервисе
/tdd         # тесты заморожены до кода
/riper       # продовый баг без активной деградации
/incident    # прод лежит прямо сейчас
/canvas      # дизайн-система → код
/decision    # архитектурное решение

# проверки
/gate-check <ID>                     # можно ли на следующую стадию
/gate-check <ID> --post-build        # сборка соответствует спеке
/gate-check <ID> --loop incident_close   # закрыть петлю инцидента
/gate-check <ID> --loop debt_close       # закрыть петлю техдолга
/methodology-check <ID>              # покрытие слоями S10-S13 + C4
/wrap                                # сверка и закрытие цикла
```

## Порядок, который не нарушается

```
что строить          →  PRD активен
   ↓
маршрут (одна строка smith, не коктейль)
   ↓
глубина записана     →  гейт знает, насколько строг
   ↓
ADI ≥3 гипотезы (Deep+)
   ↓
pre-build гейт       →  можно собирать
   ↓
сборка               →  C-coder, единственный с правом писать исходники
   ↓
аудит                →  ДРУГОЙ контекст, ground-truth из git, не из отчёта
   ↓
доказательство       →  EVID с вердиктом C4 и личностью верификатора
   ↓
guardian             →  бинарный вердикт по ВСЕЙ цепочке
   ↓
активация            →  делает оркестратор, никогда не ревьюер
   ↓
wrap                 →  drift + stale + аудит связей, REFRESH на Deep+
```

## Пять вопросов перед диспатчем

1. **Кто проверит?** Если ответ «тот же агент» — стоп.
2. **Что будет доказательством?** Если ответ «его отчёт» — стоп.
3. **Какой ярус задачи?** Если плюс — какую обвязку он покупает?
4. **Файлы пересекаются с соседом?** Если да — это не братья, это `blockedBy`.
5. **Что откатывать, если не сработает?** На A++ ответ пишется **до** старта.
